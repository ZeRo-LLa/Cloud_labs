# Сповіщення

Файл `infra/alarm.tf`. Канал доставки: AWS SNS, підписка на email. Правило: CloudWatch Alarm `f1-shop-cpu-high`.

## Умова

Середнє завантаження CPU по сервісу `f1-shop-api` вище **70%** протягом **2 хвилин** (2 періоди по 60 с, обидва мають
перевищувати поріг). Лист надсилається і при переході в тривогу (`ALARM`), і при поверненні до норми (`OK`).

### Обґрунтування

- **Чому 70%.** Автомасштабування спрацьовує при 60% (див. `AUTOSCALING.md`). Поріг сповіщення вищий, тому лист
  приходить, коли навіть із масштабуванням CPU лишається високим: це привід звернути увагу людини, а не просто
  інформація про те, що масштабування працює.
- **Чому 2 хвилини, а не одне перевищення.** Короткий сплеск CPU (один запит, прогрів, деплой) не є проблемою.
  Якщо спрацьовувати одразу, правило швидко «гойдалося» б між `OK` і `ALARM` (flapping), і листи перестали б
  сприймати серйозно.
- **`treat_missing_data = notBreaching`.** Коли даних немає (сервіс без навантаження чи щойно створений), це не
  вважається тривогою.

## Листи

> ЗАПОВНИТИ: скріншот листа про тривогу (`OK -> ALARM`) і скріншот листа про повернення до норми (`ALARM -> OK`),
> з видимим часом отримання. Не використовувати лист `INSUFFICIENT_DATA -> OK`: AWS надіслав його о 22:40 одразу
> після створення правила, до будь-якого тесту.

## Час реакції

Тест: `VUS=50` (основний прогін). Час нижче в київському часовому поясі (UTC+2); AWS у листах вказує UTC.

| Подія | Час |
|---|---|
| Початок тесту (оцінка за графіком CPU, звірити з виводом k6) | ≈ 23:16 |
| Середнє CPU вперше вище 70% (хвилина 23:19, 90,7%) | 23:19 |
| **Лист 1: `OK -> ALARM`** | **23:23:33** (21:23:33 UTC) |
| **Лист 2: `ALARM -> OK`** | **23:27:33** (21:27:33 UTC) |

- Від початку сталої фази (початок плюс 2:30, приблизно 23:18:30) до першого листа минуло близько 5 хвилин.
- Від першого хвилинного значення вище 70% (початок хвилини 23:19) до листа близько 4,5 хвилини.
- Правило було в тривозі рівно 4 хвилини.
- Лист про тривогу прийшов приблизно на 50 секунд раніше, ніж `desiredCount` змінився на 2 (23:24:23): сповіщення
  випередило реакцію автомасштабування.

### З чого складається затримка

1. Умова «2 періоди поспіль» дає мінімум 2 хвилини.
2. Метрика CPU з ECS потрапляє в CloudWatch із запізненням порядку хвилини (точну величину я не вимірював).
3. CloudWatch перевіряє стан раз на хвилину, потім SNS доставляє лист поштою (секунди).

Точний розподіл цієї затримки між складовими я не вимірював. Більш точні дані дала б історія сигналізації
(`aws cloudwatch describe-alarm-history`).

### Чому повернення до норми

Лист «OK» прийшов о 23:27:33, коли останній доступний показник CPU (хвилина 23:24) був 40,2%. Друга задача
перейшла в стан RUNNING лише о 23:24:55, тому до цього значення вона майже не вплинула. Найімовірніше, CPU впав
через спад навантаження наприкінці тесту, а не завдяки масштабуванню. Це моя інтерпретація за збігом часу; щоб
перевірити її, потрібні точний час початку тесту і графік CPU по хвилинах.

### Чи прийнятний такий час реакції

- **Для сповіщення про навантаження: так.** CPU сам по собі не означає, що користувачі страждають (у цьому тесті
  помилок було 0, p95 = 73,5 мс). Це сигнал для людини переглянути ліміти, і 4-5 хвилин не критично.
- **Для сповіщення про недоступність: ні.** Якщо сервіс упаде, користувачі відчують проблему раніше, ніж через
  4-5 хвилин прийде лист. Для таких випадків потрібне окреме правило на помилки 5xx або на стан health check з
  коротшим вікном.

## Відповіді на теоретичні питання

**Чому вимога «протягом N хвилин».** Щоб не реагувати на короткі сплески. Без неї правило перемикалось би між
`OK` і `ALARM` при кожному коливанні метрики поблизу порога (flapping), і листи ставали б шумом.

**Скільки часу від початку проблеми до листа.** Близько 4,5-5 хвилин у цьому тесті (див. таблицю й складові вище).

**Яке сповіщення корисніше для користувача.** На латентність (або на частку помилок): вони прямо відображають те,
що відчуває користувач. CPU є непрямою ознакою: у моєму тесті CPU був 90%, а латентність при цьому залишалась
низькою, тож CPU сам по собі не гарантує проблему.
